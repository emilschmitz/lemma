# Haiku 4.5 on the 6 published GenDB SEC queries: failure diagnosis (2026-10-05)

Read order followed per run (AGENTS.md "Always read the traces on failure"): `workspace/mcp_results/runs/*.json`, `submitted.json`,
leftover `declarative_build/declarative_query.rs` and the final host verify, `workspace/logs/agent_stream.jsonl`, then the launcher and
pipeline logs. `submitted.json` does not exist in any run (no run ever reached `N verified, 0 errors`, so nothing was submitted).
Traces were harvested for all six runs except q4, which never launched an agent (no `mcp_results`, no `agent_stream.jsonl`, by construction:
it died in the host export before the container started; that is a harness failure, not a missing-trace gap).
Note: thinking text is empty in every stream (`thinking` events carry `text: ""`, redacted by the Claude CLI for Haiku), so "what the agent was
thinking" below is its assistant text plus its tool calls.

Common setup facts (manifests): menu `adversary_declarative0`, `max_iterations=2`, `AGENT_TIMEOUT` 600 s (never hit; all sessions ended by the model
returning `result: success` after 4 to 7 minutes), `LEMMA_ENABLE_PARALLEL=0`, `LEMMA_ASSUMPTION_PACKAGE=sec_margin_dec`. The launcher RESULT shows
`assumption_package: unset` in `selection` for every run, but the manifest env has `sec_margin_dec`; the spec is dict-encoded (`__dict` fields) so
`LEMMA_STRING_ENCODING=dict` took effect. `LEMMA_PARALLEL_VSTD` and `LEMMA_NARROW_CELLS` are not recorded in manifest env (cannot confirm from
the run dir). The runs were on three different SHAs because the checkout moved while the batch ran: q1,q2 `fb42232`; q3 `2ac18a9`
(parallel 'auto' commit); q4,q5,q6 `600d644`. The batch is therefore not one family (AGENTS.md: do not mix SHAs).

## Q4: why no egress at all

The agent container was never started. `egress_hosts: []`, `egress_denied: false`, no `logs/docker_*`, no `agent_stream.jsonl`, no `PROMPT.txt`,
no `mcp_results/`. The run dir contains only `pipeline.log` (a single `loop_start` at 17:15:43.464) and `decl_data/cols_num.bin` (1.2 GB) and
`cols_sub.bin`. The optimizer builds the DuckDB column blobs (`decl_query_measure.py::_export_table`, table order num, sub, tag, pre) before it
renders the prompt and starts Docker. It raised `ValueError` on the third table (`tag`), at 198.5 s wall. That is the raw-escaped Rust keyword column
`abstract` (see table). Host bug, step "export", class `host_codegen`, not agent.

## Q6: the `registry.npmjs.org` CONNECT denial

`workspace/mcp_results/egress_denied.jsonl`: `{"method": "CONNECT", "host": "registry.npmjs.org", "denied": true, "ts": "2026-10-05T17:34:30Z"}`.
It was **the agent**, not the Claude CLI's own ping or plugin check. At 17:34:29 session b5af7ebb (the second session, the working one) ran a
Bash tool call: `timeout 120 sh -c 'echo "path: runquery_agent.rs" | npx -y lemma-sdk run_runquery 2>&1' | head -200`. Haiku had not yet loaded
the lazily-exposed MCP tool (`ToolSearch select:mcp__lemma-host__run_runquery` came at 17:34:33), so it hallucinated an npm package `lemma-sdk` to call
`run_runquery` through the shell. `claude_raw.jsonl` has the tool result `npm ERR! 403 Forbidden - GET https://registry.npmjs.org/lemma-sdk`. The egress
allowlist (`anthropic.com`, `api.anthropic.com`) worked as designed (denied, harmless, 0.06 ms). The `egress_denied: true` flag in the RESULT is
therefore a correct sandbox event, but it makes the run look policy-violating. Fix: tell the prompt the MCP tool names up front and that Bash cannot reach the
network (see fix 3); consider not counting a denied CONNECT from a Bash tool call as a run-level `egress_denied`.

## Cross-cutting findings

1. **Iteration 1 was a no-op in 4 of 6 runs (q1, q3, q5, q6).** In those, session 1 made 0 tool calls, lasted 1.6 to 3.9 s and the model answered
   conversationally ("What would you like me to help with?"). With `max_iterations=2` each of these runs had one real attempt, not two. Cause:
   `declarative_spec/prompt.py` (around line 640-690) builds a document with no imperative: it begins `# Declarative run_query / ## What you get`
   and ends with the lemma index; only on iteration 2 does it append `## Previous host error ... empty agent body`, which reads as a task. q2 (and
   q5/q6/q3 session 2) did start working. Host/prompt bug, class `agent_timeout`-adjacent harness waste.
2. **Every agent stopped voluntarily** (`result: success`) at 241 to 430 s of a 600 s allowance with a summary of what "would be needed". Haiku treats the
   headless run as a conversation: q5 ended asking the user a question. No timeout in any run.
3. **Prompt contradicts the CLI tool set.** The prompt says "You cannot run Verus or a shell", the CLI allows `Bash` (`--allowedTools Bash,...`). Haiku
   tried `timeout 30 verus runquery_agent.rs` (q1) and `npx lemma-sdk` (q6). MCP tools are deferred in Claude Code, so the agent first needs ToolSearch.
4. **Recurring Haiku error classes** (all inside AGENT_EDIT): `sort_by`, `HashMap/BTreeMap` iteration or `.entry()`, `for x in &mut v`, `.clone()` on OutRow,
   `as int` in exec code, helper names that do not exist (`taken_with`, `res_is_valid`), missing `valid_cols_<t>` loop invariant, missing `decreases`,
   `assume_specification` (forbidden), nested helper functions.
5. **Spec emission worked for all six** (all queries transpiled; the prompt lists "Contains: ..." warnings for q1, q2, q3, q6; q5 flagged none). No
   transpile gap and no assemble hole was seen in the five agent runs: each reached Verus with `13 to 21 verified` host functions.
6. No query got `submitted.json`; nothing measured; no execute step ran (step 7 never reached).
