## Findings

### 1. MAJOR: a dictionary-mode projection of a string column now gets a dictionary-blind example with no caveat

Old routing sent `SELECT tag, value FROM num WHERE uom='pure'` (dict) to `dict_filter` (a dictionary-aware, wrong-shape example). New routing sends it to `projection_where`: the prompt inlines `projection_where.rs` (int-only `OutRow { a, g }`, key type `(int, int)`) and says only "Your table, column and field names differ: rename them". The dict-mode spec for this query has `pub tag: Vec<u32>`, `tag__dict: Vec<String>`, `proj_key -> (Seq<char>, int)` built from `num.tag__dict@[num.tag@[i0] as int]@`, `OutRow.tag: String`. So the example does not prove a spec of this shape and nothing in the recipe section says codes must be translated through the dictionary. I grepped the whole generated prompt: no dictionary guidance in the recipe section. The same happens for `projection_top_k`, `projection_join`, `projection_distinct`, `projection_correlated_max` in dict mode (all changed from `dict_filter`: `proj_limit_noorder`, `in_subq_proj`, `proj_notexists`, `proj_distinct_join`, `proj_join_topk`, `proj_corr_exists`, `float_topk_proj`, `proj_nullable*`). Only `projection_join_correlated_max` carries the "proves in plain string mode; in dictionary mode ... adapt" sentence. Routing is closer in shape, but the description honesty problem is exactly the one in item 2 of the brief. Fix: when `f["dict"]` and recipe starts with `projection_`, append one generic sentence (string columns are `Vec<u32>` codes plus `<col>__dict`; the example's string cells are `dict[code].clone()` / `dict@[code]@` here; the dict_* examples show the translation).

### 2. MAJOR: the new parallel order defers the first submit of a verified body; this conflicts with the host's "submit again, no quota" semantics and with a 600 s wall

New order text (big-table parallel spec): "At or above the bar: submit it. Below the bar: only now try the parallel recipe ... keeping the sequential `run_id` ... (3) submit the parallel body only if it verifies and is faster; else submit the sequential `run_id`". So a verified sequential body below the bar stays unsubmitted while a multi-minute parallel proof is attempted, with `AGENT_TIMEOUT_SEC=600`. Host text (`db_extension/agent/session_clock.py:176-205`, used by `harness.py` prompts) says the opposite: "A kill at the wall saves nothing ... get a verified `submit_runquery` in while time is still left. If the session stays open, submit again when a later verified run is better. No quota." and "Call submit when a run is verified and faster than your current mark (or is your first verified success)". `AGENT_SUBMIT_ENDS_SESSION=0` is the default (`research_loop/config.env:47`), so submitting early costs nothing and is strictly safer. The backstop `measure_core.harvest_verified_submit` promotes the LATEST verified run, not the best, so a verified-but-slower parallel attempt after the sequential one would be the one scored. I could not confirm that the declarative driver appends the session-budget section (drive.py builds its own prompt), so the direct contradiction is conditional; the wall-kill and latest-not-best risks are real regardless. Fix: "submit the sequential run_id as soon as it verifies (re-submitting is free), then try the parallel upgrade and re-submit only if it verifies and is faster", unless submit-ends-session is on (then the current text is right and should say so).

### 3. MINOR: uncorrelated scalar subquery in a join projection is routed to the 700-line MAX-chain example

`SELECT s.name, n.value FROM num n JOIN sub s ON ... WHERE n.value > (SELECT AVG(value) FROM num)` (plain and dict) now routes to `projection_join_correlated_max` (was `projection_correlated_max`, 87 lines, in plain). The `sq` feature is just `\bsq_` anywhere in the spec: it does not distinguish correlated from uncorrelated, nor MAX from AVG, and the recipe also suppresses the "scalar or correlated subquery has no worked example" warning (`covered`). The 700-line "proof template, not a speed template" is a poor match; a warning would be more honest. `corr_join_nolimit` (no ORDER BY/LIMIT) is also routed to the top-k example, acceptable. Same applies to `proj_uncorr_scalar_1t` in dict mode (now `projection_correlated_max`, previously `dict_filter`; fine in shape, but covered by item 1).

### 6. MINOR: the registry test can rot silently in four ways

- `test_an_unregistered_new_fixture_would_be_caught` is vacuous: it does not create a fixture (`tmp_path`/`monkeypatch` unused); it asserts a made-up name is absent from the registry and that two real names are present. It would pass if the real test were deleted.
- `registered_examples()` dedups with `seen.setdefault`, so registering the same file twice (e.g. in `_EXAMPLES` and `MORE_EXAMPLES`, or in `_FLOAT_EXAMPLES`) silently keeps the first description and drops the second; nothing fails. Currently no duplicates (checked).
- `_ALL_FIXTURES = rglob("*.rs")`: a non-`.rs` fixture (`.json`, `.md`, `.RS`) is invisible. Currently none exist (checked).
- `test_newly_mounted_examples_use_no_banned_construct` iterates `registered_examples()` only, so the helper files (`*.helpers.rs`) are never scanned (they are clean today: `projection_null_cell.helpers.rs`, `projection_where.helpers.rs`, `projection_top_k.helpers.rs`, `projection_int_key.helpers.rs`). Its comment-stripping skips only lines starting with `//`, which is fine (strict, not lax).
Fixes are one-liners (assert no duplicate names; scan `helper_files()`; make the "caught" test copy the logic over a synthetic name list).

### 7. MINOR: `self_join_count.rs` is specialised to the test spec's `ROW_CAP_t == 4`

Its invariants contain `acc as int <= ((a.n - i) as int) * 4` and `ROW_CAP_t == 4`; the registry description ("a table joined with itself on an inequality, ungrouped COUNT(*)") does not say the proof relies on that cap. An agent copying it onto a different cap will fail on those lines. Other descriptions I checked against fixture headers/bodies and `tests/test_declarative_shapes.py`, `test_declarative_audit.py`, `test_declarative_hard_fixtures.py` are honest (see below).

### 8. MINOR: dataset/benchmark-specific text in the generic prompt

Big parallel prompt, outside the example headers: "the real 39.4M-row table", "13x on the real 39.4M-row table", "1.8x on real `pre`", "TPC-H Q1 at 3.95x", "TPC-H Q12", "TPC-H shapes", "this box shows 30 percent noise", `key_at(pre, i0)`, `uom = 'pure'`. `AGENTS.md` forbids dataset-specific names in engine code; the new test only guards `_SHAPE_LIST` (adsh/uom/stmt). Not new in this commit for the most part, but the new test gives a false impression the generic text is clean.

### 9. MINOR: "Done means ... the timed run beats the reference engine" vs the order's "submit the sequential run_id and say its speedup is below 1"

The first line of the prompt defines done as beating the reference; the order tells the agent to submit a below-bar body. Mild, reconcilable ("done" vs "best effort"), but one of the two should say it.
