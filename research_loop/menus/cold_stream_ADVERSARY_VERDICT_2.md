   - Setup: db whose `num` is `CREATE VIEW num AS SELECT qtrs FROM read_parquet('x.parquet')` (Parquet written by DuckDB `COPY ... ROW_GROUP_SIZE 122880`, 3000 distinct INTEGER values; /tmp/claude-1000/adv4/mkpq3.py, pq_e3000.duckdb, truth `SELECT SUM((qtrs=3)::INT)` = 310). `DESCRIBE` passes (INTEGER), so the glue accepts it.
   - Evidence the vector is a dictionary vector (data pointer = dictionary values, not rows): experiment main with a trace print in `zc_scalar` (build.py; `python3 scen.py trace pq_e3000`): first call `n=2048 first=[0,1352,1834,2982] sum=3078821`, but the true first 2048 rows sum to 3099190 (`SELECT sum(qtrs) FROM (SELECT qtrs FROM num LIMIT 2048)`). That call PASSED `column()` (validity all ones, aligned, non-null pointer) and was folded with the wrong cells. The next call (n=953) showed `first=[1517,1703,724,2185]` vs true row 2048.. `[1589,756,28,950]` and failed the validity check (its last validity bit is clear), so the query aborted: `ERR Invalid Input Error: a column vector is not flat, aligned and NULL-free`.
   - The real generated binaries, same databases (build_real.py, `python3 real.py r pq_e3000 pq_e5000 pq_d50 pq_e100k`): aggregate mode: `ROW 310 / 188 / 19941 / 8` = DuckDB's answers on all four. Scalar mode: rc 101 (loud panic) on pq_e3000, pq_e5000, pq_d50; correct on pq_e100k (flat vectors there). So scalar mode is the only mode with the problem.
   - I could NOT construct an all-calls-pass wrong answer: sweep.py over 90 configurations (row groups 4096..32768 rows, 2100..8000 distinct values) plus the earlier 12: every dictionary-vector case aborted loudly, every non-aborting case equalled DuckDB (0 silent differences). The guard fires because a later call (a partial vector at a page boundary) has an invalid validity bit; that is a property of the Parquet reader's dictionary child, not something the glue checks. A table where every call has a valid, large-enough dictionary is not excluded, and one passing call already folded wrong cells.

Alternative: refuse scalar mode and use the aggregate mode for non-base-table sources (aggregate flattens, verified above). Files: declarative_spec/cold_stream.py `_glue` (`main`), research_loop/menus/cold_path_feasibility.md ZC-2s item (1).

3. (a) **The SQL refusal is a blacklist regex that is untested and bypassable; keep it only as a second net and fix its inputs.** `declarative_spec/cold_stream.py` lines 137-148. Facts (refuse.py, 40 queries): DISTINCT, GROUP BY, OVER (via the word), FILTER, HAVING, ORDER BY, LIMIT, OFFSET, JOIN variants, UNION/INTERSECT/EXCEPT, WITH, WINDOW, QUALIFY, USING SAMPLE are refused in both modes (also with the quoted/commented/`$$` forms that are merely over-refused: `"limit"` as an identifier, `/* WITH */`). NOT refused: `TABLESAMPLE` (the `\bsample\b` does not match inside the word), `FETCH FIRST`, comma joins, subqueries/IN-subqueries, `LATERAL`, table functions in FROM (`read_parquet(...)`), `PIVOT`/`UNPIVOT`, `FROM x SELECT`, `AT (...)`, a `;` second statement, comment-split keywords (`GROUP /*c*/ BY`), and `E'\''` strings hide a following `GROUP BY` from the quote-blanking regex (DuckDB honours the backslash escape, the regex does not). Today the transpiler stops all of these except FETCH (finding 2), so none is a silent wrong answer, but the cold net is not what stops them. Two further gaps: (i) `assemble_cold_program(..., sql=None, reference_sql=None)` skips the check entirely (all test calls do), so the check is opt-in per caller; (ii) no test covers it. Fix: make `sql` a required argument; replace the blacklist with an allowlist on the sqlglot tree (exactly `Select(<aggregates>, From(single Table), optional Where)`, nothing else set in `args`); two tests per refused family (DISTINCT form, FETCH/TABLESAMPLE/comma join) plus the accepted shapes. DISTINCT specifically: refused by the spec scan (`distinct` in the spec text) AND by the regex, both modes, with and without `sql=` (transp3.py: `refused ... the spec talks about DISTINCT values`).
