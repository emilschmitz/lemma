# Adversary verdict: LEMMA_TARGET_CPU (default x86-64-v3)

Verdict: ACCEPT WITH FIXES.

## Findings

1. Behaviour of proved code. No semantic change found. Rust/LLVM does not contract a*b+c into FMA or reassociate floats without explicit opt-in, so f64 results are unchanged by v3 (the f64 idealization in emit.py is therefore unaffected). Integer overflow/panic semantics are not target dependent. Verus verifies source before rustc codegen; flag only on the rustc side. Residual risk: explicit `mul_add`, `f64::exp/ln/pow` (libm vs intrinsic selection) and autovectorized float reductions are not reassociated, but the "byte-identical ROW lines on 7 bodies" evidence covers only those 7. Low risk, no fix needed beyond keeping the identical-output check as a gate in any A/B.
2. Speed-claim honesty. Not yet disclosed enough. Duck is a prebuilt baseline binary (runtime dispatch only for some kernels); ours gets AVX2/BMI2/FMA. That is a legitimate "same box, our best reasonable build" comparison only if every quoted speedup states the target CPU class (and that generic gives less, e.g. scan 15.2 vs 11.9 ms, Q6 34.9 vs 25.1 ms). Evidence weaknesses: machine loaded 4-10 by other jobs; only 3-5 invocations; the headline wins (scan, Q6, Q12) are 1.3-1.4x and plausible but within what load noise can fake. Q12 "native 2.2x slower" is a single large outlier, the one claim that is likely robust. v3 as default is acceptable (never worse than generic in the data, ties elsewhere). Required extra run before quoting any v3 vs generic gain: scan, Q6, Q12 on an idle machine, >=7 interleaved alternations generic/v3 under flock, report medians and min/max.
3. Portability. v3 binary SIGILLs on CPUs without AVX2/BMI2/FMA (pre-Haswell, some old/virtualised CI, QEMU default CPU). Nothing detects it: a SIGILL would print no QUERY_LATENCY_US and surface as a generic run failure, which could be misread as a software/pin fail. Also the target is read from env at compile time, while container build and run hosts could differ. Plumbing: pipeline.py, run_artifacts.effective_settings, declarative_manual _JOB_ENV_KEYS and container_batch env all updated and consistent (default string "x86-64-v3" duplicated in two places). GAPS: `target_cpu` is only added inside _apply_speed_bar and is DROPPED by declarative_spec/drive.py success dict (lines ~355-362), db_extension/verus_bridge.py _SPEED_KEYS, declarative_manual.check()'s printed key list and declarative_remeasure KEYS. So per-job result records and printed output lack it; only last_check.json and effective_settings carry it.
4. Code bugs. None functional. Legacy paths (research_loop/harness.py, speed_bench/measure.py, holdout) still hard-code target-cpu=native, which is the config shown to be 2.2x slower on this host; they are not the declarative path but their numbers must not be mixed with v3 numbers. Typo-ed CPU name is passed straight to rustc (fails loudly, fine).

## Required fixes
- Propagate `target_cpu` into drive.py success record, verus_bridge._SPEED_KEYS, declarative_remeasure KEYS, and the manual check print.
- State in the quoted-speedup template/docs: "binary built with -C target-cpu=x86-64-v3 (AVX2/BMI2/FMA); DuckDB prebuilt baseline".
- Idle-machine re-run of scan/Q6/Q12 (generic vs v3, >=7 alternations) before claiming gains.
- Note SIGILL/portability in the flag docstring (run host must support v3; use LEMMA_TARGET_CPU=generic for unknown hosts).
