# Adversary verdict: Q5 dense slot fix (b168d5e, 2e93645)

PASS WITH FINDINGS. The Q5 failure class (a hash body killed after the proof by a host assert in `main`) is fixed. But the replacement guard is a regex lint that is easy to slip past, so a proved program can still allocate a huge dense table at run time. Nothing at run time catches it now, because the assert was removed.

Repro for 1-4: `PYTHONPATH=. uv run python <script>` that loads `research_loop/generated/manual/q5real/context/ro/spec.rs` and `decl_data/expect.json["dict_sizes"]` and calls `dense_budget.body_violation(body, spec, dict_sizes)`. Key slot count at real sizes is 1.06e16.

1. **Product lint evaded by trivial rewrites (major).** `declarative_spec/dense_budget.py:131-158`, `_alloc_sizes` at :195-198. Only `vec![x; E]`, `with_capacity(E)` and `.resize(E, ..)` are inspected, and only when `E` textually contains two or more `<t>.<c>__dict.len()` (after alias substitution) plus a `*`. All of these return None (verified, none flagged) with m1 = `s.name__dict.len()` and m2 = `p.tag__dict.len()`:
   - `let t = m1 * m2; vec![0u64; t]` (an intermediate `let` is not tracked).
   - `vec![0u64; (m1 as u64 * m2 as u64) as usize]`.
   - `Vec::from_elem(0, m1*m2)`.
   - `resize_with(m1*m2, ..)`.
   - `vec![0; m1.checked_mul(m2).unwrap()]`.
   - `iter::repeat(0).take(m1*m2).collect()`.
   - `fn sz(a,b)->usize{a*b}` helper (helpers are admitted separately).
   - Vec of vecs: `while i < m1 { g.push(vec![0; m2]) }`, which allocates the full grid.
   - A push loop bounded by `while k < m1 * m2`.

   The same bodies panic or abort at run time with capacity overflow or OOM once compiled. Fix: do not pattern-match expressions. Evaluate sizes, e.g. by rejecting any `__dict.len()` alias that appears in a `*`, `<<` or `checked_mul`/`saturating_mul` expression with another dictionary length (taint through `let`). Or add a runtime guard that is NOT a host assert on the hash path, such as a wrapper allocator or an allocation cap in the `run_query` harness that reports "agent allocated N bytes, over budget". Failing loudly at run time is acceptable only if the prompt already said so.

2. **Lint is off whenever `dict_sizes` is missing, even if declared widths already prove it too large (major, silent no-op).** `dense_budget.py:123` returns None when `not dict_sizes`. `report` falls back to declared bounds (u8=256, u16=65536) for the prompt, but `body_violation` does not use them. Also, when only some sizes are present, `:150-153` returns None as soon as one factor is missing, even though a declared cap exists. Repro: `body_violation(base, spec, None)` and with `{'sub.name': 9646}` both give None. Where this happens:
   - `speed_bar is None` in `pipeline.py:307` / `drive.py:236`. That is every synthetic run, every run without a measure DB, and the lemma-assumptions path.
   - An older workspace `expect.json` without `dict_sizes`. `bench.load_speed_bar` (`bench.py:136-148`) returns the raw JSON, so `.get("dict_sizes")` is None and nothing warns.

   The prompt then says "actual dictionary sizes were not measured" (`prompt_section`), which is the only trace. Fix: in `body_violation` use `declared_slots`/declared caps as the size when an actual is missing, and make the run say once that the lint is inactive (the repo rule is no silent fallbacks).

3. **False positive: nested loops over two dictionaries are flagged even with no allocation (minor).** `dense_budget.py:131-143` and `_nested_dict_loops` at :161-173. A body like `while a < s.name__dict.len() { while b < p.tag__dict.len() { b += 1 } a += 1 }` (no vec at all) returns a violation. The check is on loop nesting, not on allocation. A legitimate per-pair probe that is O(dict1 * dict2) time is a different problem (slow), but it is not the dense-table problem and the message is wrong. Also, `aliases = dict(...)` keeps only the last `let m1 = ...` when the same name is re-bound to different dictionaries in different scopes, so an alias can resolve to the wrong dictionary (false positive or negative). Fix: require a `push`/`vec!`/index-write into a table sized by the loop bounds, and scope the aliases.

4. **Single-dictionary and per-slot allocations are not covered (minor, by design but not stated to the agent beyond "ONE small dictionary is fine").** `vec![false; p.plabel__dict.len()]` (698k) per group, or a `vec![false; adl]` inside a loop over groups, passes the lint (verified). Memory is groups x dict, so a hash body that keeps a per-group seen-array for COUNT DISTINCT over a 698k dictionary with many groups can OOM at 39.4M rows after the proof. The lint sees only the first factor. Fix: treat an allocation inside a loop whose bound is another dictionary length (or the group count) as a product, or put the per-group-distinct pattern in the prompt with a budget on the product.

5. **Fixture sizing is only checked at real SEC dictionary sizes for key lints; run-time sizing assumptions in the dense fixtures are not catalog-checked (minor).** `hard/dict_group_two_keys_count_distinct_avg.rs` hardcodes `st*256+rf`, `cnt.len() == 65536` and a per-slot `seen` of `adsh__dict` length each (:3, :9, :212, :289). That proves for u8 codes, which the exporter guarantees by refusing a dictionary above its declared width (`decl_query_measure.py:314`, a prepare-time refusal, which is good). On a catalog where `adsh` is 86k entries, 65536 slots x 86k bits is 5.6 GB at run time. The lint cannot see it, since only `key_at` columns are checked and the `seen` allocation is not a product of two dictionary lengths in one expression. Same class as 4. Fix: a one-line prompt note that a per-slot allocation over a third dictionary multiplies, plus the loop-nesting rule from 4.

6. **Other host asserts remain in the assembled `main`, data-dependent and only partly visible in the prompt (minor).** `assemble.py:191-208` (join cap: builds a `HashMap` of cloned right-table key tuples over the whole table, so Q5's `num` x `pre` check is a 9.6M-entry map of String-tuple clones, run before the timed section; memory and time are not mentioned to the agent), `:269` (row caps), `:285-333` (value bounds, dictionary membership and uniqueness, `HashSet` of all dictionary entries), `:347` (declared unique key, `HashSet` of every row key), `:429` (rows == DuckDB pin). These are catalog assumptions (the repo treats them as such), and the exporter measured them, so a failure means the data changed after prepare. The exposure that remains is only time and memory of the checks on the 39.4M-row table. Suggestion: print the timing of the host checks separately, so a slow `main` is not charged to the agent's body.

No finding on code width: the exporter refuses at prepare time when a dictionary exceeds its declared width (`decl_query_measure.py:314`), so a u8/u16 overflow cannot first appear at run time.
