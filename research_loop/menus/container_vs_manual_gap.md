# Container Claude agent vs manual provers: why the gap (read-only analysis, 2026-10-05)

Question: manual provers (Sonnet subagents driving `research_loop/scripts/declarative_manual.py`) proved many GenDB-shaped queries; the
container agent (`run_container_agent.py` -> `db_extension/optimizer.py` -> `declarative_spec/drive.py` -> docker `claude -p`, MCP
`run_runquery`/`submit_runquery`) with Haiku 4.5 mostly fails the published queries. Everything below is read from the repo, `PROMPT.txt` and
traces in `research_loop/runs/` (traces order followed: `mcp_results/runs/*.json`, `submitted.json`, `agent_stream.jsonl`, `claude_raw.jsonl`).
No code, container, Verus or GCP was run.

## 3. Prompt each side gets (answers to question (a))

* Same function: `declarative_manual.prepare()` calls `build_declarative_prompt(... in_docker=False ...)` and writes `context/ro/DECLARATIVE.md`; the
  container calls it with `in_docker=True` from `drive.py:218-227` and pipes the string as `PROMPT.txt`. Diff of Q2 `PROMPT.txt` vs `DECLARATIVE.md`
  after removing `/workspace/` is empty. Same `context/ro` content: both call `drive._ensure_context_files` (spec, query.sql, schema.json,
  lemma_index.md, `verus/` vstd + guide + LEMMAS.md, `examples/`). Only the mounted example set depends on `LEMMA_STRING_ENCODING` (`mount_examples`):
  dict mode mounts `dict_*.rs` and `hard/dict_*.rs`, plain mode does not (`tests/test_declarative_string_dict.py:502-505`).
* Same env axes only if the manual job's snapshot says so: `_JOB_ENV_KEYS` (`declarative_manual.py:137`) is whatever the preparer's shell had. Container
  fixed values: `LEMMA_STRING_ENCODING=dict`, `PARALLEL_VSTD=auto`, `NARROW_CELLS=0`, `sec_margin_dec`, `speed_bar 1.0`.
* Not the same: the coordinator's brief to the manual subagent and its tool set (no prompt in repo).
* Previous-error section: container iteration 2 appends `## Previous host error` (last 4000 chars); the manual prover sees every check in its own context.

## 4. Where the manual successes came from (fairness of the comparison)

Many of the "proved" shapes were proved on the local synthetic slice in plain string mode, by a prover that could iterate with the repo open, and
then frozen as fixtures that the container agent receives as examples: that is the same loop the container agent is now asked to run closed-book.
The published-shape hard fixtures (`dict_group_two_keys_count_distinct_avg`, `dict_having_scalar_subquery`, `dict_anti_join_group_topk`,
`dict_join3_group_topk`) were made after the Haiku pub6 failures, so they are the manual prover's solution to exactly the queries Haiku failed, and
Q1 flipping to a pass after the first one landed (T191606Z) is the clearest evidence that example coverage, not check budget, is what moves results.

## 5. Suggested order of work

1. Fix `spec_shape` dict-mode ordering and mount `hard/projection_join_correlated_max_topk.rs` (Q2) and all `hard/*.rs`; rerun Haiku Q2/Q3/Q4 (cheap).
2. Resolve the Q5 dense-slot panic before any further Q5/Q6 run (host side: refuse or avoid the dense slot table when the product exceeds the budget).
3. Reset the body to the best-so-far at iteration 2; strip the `Cols_*` warnings and send errors first-N instead of last-4000.
4. Finish the Sonnet container run on Q2 (started 20:36 UTC) and add Q3/Q4; one Haiku manual run. That gives the 2x2 and tells how much remains for the model.
