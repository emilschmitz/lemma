## Compile status

No LaTeX toolchain on this machine (`pdflatex`, `latexmk`, `tectonic` all missing), so the TikZ and the
`listings` blocks were **not compiled**. They use only plain constructs (rectangles, nodes, polylines,
`arrows.meta`, `lstlisting` in minipages). The SVGs are rendered from the same description and were
checked visually (`rsvg-convert`); fonts differ from the Libertine of the paper, so text widths in the
real PDF will differ slightly. First thing to do in Overleaf: compile, and nudge box widths if a line
overflows. The `figure*` width assumes the ACM sigconf text width (about 17.8 cm); the overview is 17.5 cm.
To compile: add the preamble lines from `snippets.tex`, upload `figures/`, use the two `figure*` blocks.

## Where each fact comes from

Overview:
- Chain and README flow: `README.md` "How it works".
- Spec = ground truth, `valid_cols` from catalog caps, `requires`/`ensures`: `declarative_spec/emit.py`
  (`emit_declarative_spec`), regions in `declarative_spec/regions.py`.
- Catalog = schema + assumption package, measured on the data, user-approved, re-checked at load:
  `README.md` "Using it on your own data"; loader `assert!`s in `declarative_spec/assemble.py` (`_runtime_checks`).
- Sandbox: `research_loop/agent_sandbox.py` (`docker run --network none --memory 3g --cap-drop ALL`,
  `context/ro` mounted `:ro`, workspace rw, `lemma-mcp.sock`, `lemma-egress.sock`);
  `docker/agent/entrypoint.sh` (egress sidecar, mcp.json); `research_loop/AGENT_SANDBOX.md`
  (Claude Code, egress only to the Anthropic API, WebSearch/WebFetch denied).
- MCP tools `run_runquery`, `submit_runquery` (submit ends the session): `db_extension/agent/mcp_tool_registry.py`,
  `db_extension/agent/session_clock.py`.
- Admission (rejects `assume`, `admit`, `external_*`, `use` other than broadcast groups, forbidden names; helper
  region only `proof fn`/`spec fn`; name clashes with host names) and "only the marked regions survive":
  `declarative_spec/admit.py`, `declarative_spec/pipeline.py` (`run_declarative_metrics`), `declarative_spec/assemble.py`.
- Verus + compile (`verus --compile`, N verified, 0 errors): `declarative_spec/pipeline.py` (`compile_and_run`).
- Run: pinned DuckDB columns exported to `decl_data/cols_*.bin`, DuckDB reference rows and all-core timing
  (`duck_threads`), rows compared (`rows_match_error`), speed bar: `declarative_spec/drive.py`
  (`_maybe_large_table`), `declarative_spec/pipeline.py` (`_apply_speed_bar`).
- Trusted set, adversary gate: `docs/TRUSTED_FAMILIES.md`, `research_loop/menus/TRUSTED_ADDITION_PROTOCOL.md`,
  README "Trust". The transpiler (SQL means the spec) is drawn as trusted: the README status says a corpus-wide
  check of every spec against DuckDB is not done.

Listing: the spec is the real output of `emit_declarative_spec("SELECT SUM(line) AS total FROM pre WHERE line > 5",
{"pre": {"line": "BIGINT"}}, assumption_package("sec_margin_dec"))`. The body is the Haiku body from
`research_loop/runs/20261005T010536Z_q961230_9284ffeb/workspace/runquery_agent.rs` (the run's `submitted.json`:
5 verified, 0 errors). I re-assembled the emitter spec with that body (`assemble_declarative_program`) and
verified it with Verus 0.2026.07.18: **5 verified, 0 errors**. Without a catalog the emitter writes
`pre.n as int < 0x8000...int`, which Rust parses as generics; that form never occurs in real runs, so the listing
uses the catalog form.

## Simplifications and open points (so nothing is drawn that is not true)

- Listing: the emitted `ensures` is one conjunction (`(true && len == 1 && forall r ...) || (!true && len == 0)`);
  it is shown split. The `use` lines, `OutRow`, `row_hit`, `sum_total_val` and three proof asserts are omitted.
  The original Haiku run used the parallel spec variant (an extra `pre_arc` parameter); the listing is the
  sequential variant, which verifies with the same body.
- The agent file starts as a copy of the spec; only the `AGENT_EDIT` and `AGENT_HELPERS` regions are used.
- UNCERTAIN, not drawn: the exported column files `decl_data/cols_*.bin` are written under the workspace
  directory (`declarative_spec/drive.py`), and `agent_sandbox.py` mounts the whole workspace read-write at
  `/workspace`. Unless the launcher separates them, the agent can see the exported columns. Figure 1 does not claim
  that data stays outside the sandbox. Worth checking before the paper says so.
- Timing lock (`flock /tmp/lemma_timing.lock`) and memory guard (`scripts/ram/verus_guarded.sh`, container 3 GiB) are
  operational scripts around the pipeline, not pipeline stages; left out of the figure.
